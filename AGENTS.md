# fasthep-flow Agent Instructions

These instructions apply when working in the standalone `fasthep-flow` repository.
The Python package is `hepflow`.

## Ownership

`fasthep-flow` owns the domain-light FAST-HEP workflow core:

- workflow YAML loading, includes, normalisation and lowering;
- logical graph and data-flow analysis;
- execution plan models and compiler artifacts;
- runtime orchestration and artifact lifecycle;
- registry/profile loading and extension contracts;
- backend interfaces plus the baseline local backend.

It does not own domain implementations:

- Dask, HTCondor and other production infrastructure backends belong in
  `fasthep-distributed`; Flow owns only the core backend contract and
  orchestration boundary.
- HEP analysis operations, ROOT/awkward IO, histogram filling and cutflows
  belong in `fasthep-carpenter`.
- Metadata inspection, diagnostics, schema snapshots and provenance tooling
  beyond Flow's runtime records belong in `fasthep-curator`.
- Plots, reports and visual rendering outputs belong in `fasthep-render`.
- CLI commands belong in `fasthep-cli`; Flow should expose public APIs for them
  to call.

## Core Contracts

- `src/hepflow/api.py` is the public facade. Keep it small: parse/delegate/return
  public objects rather than implementing compiler or runtime internals there.
- `src/hepflow/model/` contains typed workflow, graph, plan, data-flow,
  lifecycle, resource and extension-contract models.
- `src/hepflow/compiler/` turns author workflow input into explicit,
  backend-independent artifacts and plans. Key areas include normalisation,
  includes, graph lowering, dependency analysis, output claims, systematics,
  compile hooks, registry resolution and plan generation.
- `src/hepflow/runtime/` consumes compiled plans and orchestrates execution,
  materialisation, partitions, hooks, provenance records and writer manifests.
- `src/hepflow/backends/model.py` defines backend contracts; keep concrete
  infrastructure-specific implementations outside Flow unless they are the
  minimal local baseline in `src/hepflow/backends/local.py`.
- `src/hepflow/registry/` and `src/hepflow/profiles/` load built-in and
  extension-provided capabilities. Preserve the registry/profile extension
  mechanism rather than hard-coding companion packages.

## Validation

Use the smallest relevant test while developing. Before handing off a broad
change, run `pixi run check` and `pixi run test`.

CI additionally validates the supported Python environments and package
distributions; keep `pixi.toml` and workflow matrices aligned when changing
Python support.

## Public API and Compatibility

- Preserve `hepflow` import compatibility and the typed package marker
  `src/hepflow/py.typed`.
- Prefer adding public orchestration functions in `hepflow.api` that delegate
  to focused compiler, registry, backend or runtime modules.
- Do not expose runtime-only implementation details in author-facing workflow
  YAML when they can be derived from existing specs, defaults, `requires`,
  `provides` or registry metadata.
- Keep compiler outputs explicit and inspectable even when author YAML is
  concise.
- Treat extension contracts as public surface area. Update tests and docs when
  changing models, registry schema, hook signatures, backend APIs or generated
  plan shape.

## Generated Files and Special Care

- Do not edit `src/hepflow/_version.py` by hand; it is generated by
  `hatch-vcs`. Keep `src/hepflow/_version.pyi` aligned if the public typing
  surface changes.
- Do not commit caches or build products such as `__pycache__/`,
  `.pytest_cache/`, `.mypy_cache/`, `.ruff_cache/`, `.pixi/`, `build/`,
  `dist/` or `docs/_build/`.
- Docs archives under `docs/archive/` are historical reference material. Prefer
  updating active docs under `docs/authoring/`, `docs/execution/`,
  `docs/extending/`, `docs/getting-started/`, `docs/developer/` and
  `docs/reference/`.
- Runtime/compiler artifact paths such as `compile/`, plan YAML, dependency
  YAML, reports, manifests and benchmark output are products of workflows or
  tests; avoid checking them in unless a test fixture intentionally needs them.

## Output Artifact Layout

Writer sinks (`write:` blocks, for example `root_tree`) are sink-agnostic about
where files go; `hepflow.build_layout.BuildPaths` and the writer path rules own
the layout. Workflow authors set only a `path`:

- A relative `path` is placed under `<outdir>/artifacts/files/`.
- With `when: partition_end` (the default for non-render sinks) and no path
  tokens, `skims/x.<suffix>` becomes
  `artifacts/files/skims/x/<dataset>/<part>.<suffix>`: the path stem names a folder,
  each dataset gets its own subfolder, and each partition one file.
- `<part>` is `<file_index>_<chunk_index>` (`0_0`, `0_1`, `1_0`, ...); without
  event chunking it is `<file_index>_0`. `<file_index>` is the position in the
  dataset's `files` list.
- Explicit tokens `{dataset}`, `{part}`, `{partition_id}` and `{node_id}` in
  `path` replace the default and are used as written. An absolute `path` is kept
  as is, outside the build directory.
- Each writer gets `artifacts/files/<writer name>/manifest.json` listing every
  file per dataset (path, partition, attempt, entries, size, provenance record).
  `name` is the writer name or the path stem; when the stem is only a token
  (`{dataset}/{part}.root`) the writer is named after its node id
  (`write.FilterChannel.0` becomes `FilterChannel_0`).
- A backend that delivers writer outputs itself (for example HTCondor sending
  job-directory files to EOS) sets the context entry `output_files_root`. Then
  the `files` family resolves below that directory instead of
  `<outdir>/artifacts/files`; a relative root is resolved against the working
  directory of the process that writes (`.` is a job directory). Only `files`
  moves; cutflows, histograms, provenance and the manifests stay below `outdir`.
  Writers' manifest entries are rewritten to `path_type: relative_to_files_root`
  with the path relative to that root and an `adler32` checksum of the file, and
  the optional context entry `output_destination` is recorded as `destination` on
  the writer manifest: a file is at `<destination>/<path>` once the backend has
  delivered it. Delivery itself is the backend's job, not Flow's.
  `hepflow.build_layout.partition_output_roots(plan)` lists the top-level entries
  below the root that partition writers create (the first path component, with
  `{dataset}` expanded), so a backend knows what to deliver before the run.
- Two writers may not claim the same path; the compiler rejects collisions
  (`compiler/output_claims.py`). Resolution happens in
  `runtime/handlers.py`, manifests are written by
  `runtime/writer_manifests.py`.

Example (workshop `04-save-data/01-skims`, `path: dimuon_candidates.root`):

```text
artifacts/files/dimuon_candidates/
├── data/0_0.root
├── dy/0_0.root
└── manifest.json
```

## Testing Expectations

- Compiler changes usually need focused tests in `tests/compiler/` covering
  normalisation, graph lowering, dependency/data-flow reasoning, output claims,
  systematics, hooks or plan generation as appropriate.
- Runtime changes usually need focused tests in `tests/runtime/` covering plan
  execution, partition handling, materialisation, hooks, provenance or artifact
  records.
- Backend contract changes should include `tests/backends/` coverage and should
  avoid importing `fasthep-distributed` implementation details.
- Public API changes should include `tests/api/` or `tests/model/` coverage and
  preserve existing import paths where practical.
- For broad contract changes, run at least `pixi run check`; for narrow changes,
  run the smallest relevant tests plus `pixi run lint` when Python files change.
